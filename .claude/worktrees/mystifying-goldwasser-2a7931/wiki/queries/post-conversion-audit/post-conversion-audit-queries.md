# Post-Conversion Audit Queries

The canonical battery of SQL audits a DC (or QA analyst) runs after a plan converts to verify takeover data is clean and ready to go live.

## Purpose

After a plan converts, data lands on PRK in the `CORP.*` and `PENSION.*` tables. Before the plan can go live, someone has to prove the data is sane. These queries do that work.

Each query targets a specific failure mode observed in prior conversions:

- **Balance residuals** — Money parked under dummy SSNs (`999-00-0000`) that never got allocated to real participants.
- **Wrong takeover-type codes** — `BILL_REMIT_DETAIL` rows whose `TAKEOVER_TYP_C` does not match the `TR_NO` / `DEP_EFF_DT` combination (codes 12 / 13 / 14 / 15 / 16 carry different semantics for mutual-fund re-reg, PCRA, brokerage, stock-fund, blended).
- **Employee-table anomalies** — Participants with "BENE", "ESTATE", "QDRO", or "ACCOUNT" in their name who are not coded as beneficiaries (`PART_STAT_CD <> 8`) and therefore will hit downstream reporting with real-person logic.
- **EDS duplicate-SSN messages** — File-load errors surfaced from `EDS_LOAD_DATA_MSG`, joined back to the uploading file-services user (Schloat, Coombs, Coccaro, Forstner, Besler, Essell, Nikischer, Sanford, Fortune, Tocci, Walker, Vrba, Sama).
- **Loan integrity** — 11 distinct loan audits: rollover-payment reprocessing, multi-loan `INTL_LN_REF_NO` sequencing, semi-monthly `FST_BILL_DT`, first-repay-day-of-month, `LN_COUPON_CD = 'P'`, `ACTUAL_DIV_TKOVER_D` population, origination date vs conversion date, outstanding > original, deemed amount < outstanding, source-balance vs initial-balance reconciliation.
- **Missing elections / PX subscription mismatches** — Participants in `AUDIT` with no `PART_ELECT_DETAIL` rows; Portfolio Express defaults lacking the matching `PART_SERVICE_DATA` subscription.
- **Deferrals** — Excluded employees with deferrals, terminated employees with active deferrals, ineligible employees with deferral data flagged not-transmit, suspended-participant transmit-code check.
- **Eligibility / kit dates** — Missing or wrong `KIT_MAIL_D` vs `CLIENT_KIT_MAIL_D` (driven by `MAIL_OWNER_C`), trued-up eligibility dates in the future, pending eligibility with past dates, employees missing from eligibility entirely.
- **Vesting** — Participants hired before the last plan anniversary missing `EE_CREDITED_SRV` rows; BENE/QDRO participants without the `VEST_SCHD_EFF_DT = '19500101'` bypass row.
- **Basis & YTD contribs** — Missing basis rows for takeover contributions; after-tax / Roth basis verification; pre-'87 basis sanity; missing YTD contrib rows for active participants.
- **Auto-enroll / auto-escalate** — Default percentage matches `AUTO_ENRL_DEF_P`, auto-enroll date populated when transmit-code = T, and a large CTE that projects each participant's expected escalated percent forward and flags those whose `DEF_P` doesn't match (`auto_enrl_def_p + periods <> def_p`).

The queries are built on two temp tables:

- `AUDIT` — One row per participant, carrying `CASE_NO`, `ENRL_PROV_GRP_I`, `SOC_SEC_NO`, `PART_ENRL_I`, and `A_CASE` (the sibling "A" plan for plans with more than 20 funds). Every other query joins back through `AUDIT`.
- `AUDITSRCDATA` *(legacy only)* — Held `(ENRL_PROV_GRP_I, CTRB_TYP_CD, SRC_I, MAIL_OWNER_C)` for source-level lookups. Dropped from the NEW version because the same data is pulled inline.

## When to Run

- Immediately after a plan's takeover batch load completes.
- Again before go-live, after corrections have been applied.
- As part of the formal final takeover audit deliverable sent to TM / TC ([[final-takeover-audit]], [[audit-pack]]).

Update the header parameters before each run:
- `CASE_NO` in the `INSERT INTO AUDIT` block.
- `DEP_EFF_DT` in the `BILL_REMIT_DETAIL` check (two dates: the 1006 contribution effective date and the 1119 transfer effective date — usually consecutive days).
- `SRC_I` values for after-tax, Roth, vesting, and deferral sources.
- Plan effective date in the loan-origination-after-conversion check.
- Prior plan anniversary date in the vesting and YTD-contrib checks.

CREATE TABLE AUDIT

AND PART_I=PERSON_I AND ACCOUNT_NO=CASE_NO AND EE.SOC_SEC_NO=PS.SOC_SEC_NO

### 26. Auto-escalate projection — expected percent vs actual (big CTE)

The final `SELECT` flags rows where `auto_enrl_def_p + periods <> def_p` — i.e., the participant's current deferral % is out of sync with what auto-escalate would have produced. Results go to TC/TM for client conversation.

## Output / What to Look For

Every query is designed to return zero rows on a clean plan. Anything that comes back is a defect to investigate:

- **Dummy-SSN residuals** → the DC must move money to the correct participant and reverse the dummy-SSN entry.
- **Wrong TAKEOVER_TYP_C** → Operations corrects the BILL_REMIT_DETAIL row before year-end reporting runs.
- **BENE / ESTATE / QDRO misnamed participants** → update `PART_STAT_CD` to 8 or 9.
- **Loan checks that also emit an UPDATE** → run the UPDATE after confirming the SELECT results; iterate `INTL_LN_REF_NO` counter until no rows remain.
- **Missing elections / default subscription gaps** → participant will hit QDIA incorrectly; fix via Enrollment or a PRK override.
- **Auto-escalate projection rows** → send to TC/TM as a report; client decides whether to apply the missed escalations or leave the participant at the current percent.
